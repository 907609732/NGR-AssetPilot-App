# NGRAI辅助UI切图命名工具 V2.2 升级说明

对比基线版本：V1.43  
当前版本：V2.2  
更新日期：2026-06-01

## 一句话总结

V2.2 不是一次普通迭代，而是一次产品形态升级：工具从“能帮忙命名的网页”进化为“面向项目组资产规范、AI 命名、切图检测、跨设备配置分发的大批量 UI 资源治理工作台”。

如果说 V1.43 解决的是“图片怎么改名”，那么 V2.2 开始解决的是“一个项目组如何长期、稳定、低失误地管理切图命名规范”。

## 核心升级价值

### 1. 架构升级：从单体脚本进入模块化工程

V1.43 主要依赖单个 `app.js` 承载几乎全部业务逻辑。随着 AI 接入、知识库、检测规则、导入导出、翻译、批量性能不断叠加，单文件模式已经接近维护极限。

V2.2 已完成模块化拆分，核心能力被拆分到 `js/` 目录：

- `config.js`：项目、方案、AI、检测配置
- `state-dom.js`：全局状态和 DOM 引用
- `uploads-editor-translator.js`：上传、编辑、翻译交互
- `ai-workflow.js`：AI 命名与本地知识库命名流程
- `assets-detection.js`：UI 切图检测逻辑
- `rendering.js`：列表渲染与界面刷新
- `naming-knowledge.js`：命名词库、语义规则、翻译辅助
- `export-template-storage.js`：导入导出、模板、持久化
- `lifecycle-rules.js`：生命周期、规则校验、事件绑定
- `toast.js`：提示反馈

这次拆分让后续改代码更安全，也更省上下文：以后修改某个功能，不需要把整个巨型 `app.js` 都读一遍。

### 2. 性能升级：开始面向万级图片批量处理

V1.43 在大批量上传时容易出现页面卡死，尤其是一万张图片这种极限场景，浏览器会同时被文件读取、图片解码、预览生成、列表渲染拖垮。

V2.2 做了针对性性能优化：

- 上传改为分批处理，降低瞬时主线程压力。
- 图片读取加入并发控制，避免一次性把浏览器资源打满。
- 列表改为分页式渲染，只渲染当前需要展示的图片。
- 图片预览链接改为懒加载，只给真实显示出来的列表项创建预览。
- 删除和清空时主动释放对象 URL，减少内存残留。
- 重复资源检测默认关闭，避免大批量场景下做无意义重计算。
- 超大批量图片自动跳过高成本重复比对，优先保证工具可用性。

这意味着 V2.2 的目标不再只是“能跑”，而是开始考虑“项目真实资产量级下能不能稳稳跑”。

### 3. 命名系统升级：从 AI 推荐变成项目级命名规则引擎

V1.43 已经具备 AI 命名和基础知识库能力，但命名结构、项目配置、单图细节调整还不够体系化。

V2.2 重点补强了命名全链路：

- 支持项目与项目配置方案分离，一个项目下可以有多套命名方案。
- 默认内置 NGR 项目，并保留更多项目扩展入口。
- 支持当前界面工程名、当前界面命名、前缀名分开填写。
- 前缀支持 `无`、`T_UI`、`T_UI_Img`、`T_UI_Icon`。
- 待处理图片列表内也拆分前缀名、工程名、界面名，方便逐张微调。
- 支持批量追加后缀。
- 支持批量添加序号，按 `01, 02, 03, 04` 追加到命名末尾。
- 支持按原文件名排序，便于状态图、序列图、按钮组统一命名。
- 支持完整模式和紧凑模式切换，既照顾 AI 辅助，也照顾熟悉英文命名的高频用户。
- 新增“只使用本地知识库命名”，在没有 AI 或不想调用 AI 时也能完成批量命名。

命名知识库也进行了多轮规则收敛：

- 禁止语义名中出现 `Module`。
- 中文“底、背景、底图”等优先命名为 `BG`，不再输出冗长的 `Background`。
- `Reward` 统一修正为 `Rewards`。
- 支持状态词、结构词、方向词、颜色词、图标词、背景词等分类词库。
- 词库面板改为标签页，可按分类点选，不再占用过多列表高度。
- 词库选词支持再次点击取消，更接近真正的可选项交互。

### 4. AI 与翻译升级：从单一接入变成可迁移配置能力

V2.2 对 AI 和翻译配置做了更工程化的处理：

- 支持 OpenAI、Kimi、兼容 OpenAI 格式的大模型服务，以及自定义模型接口。
- AI 配置支持保存、测试、导入、导出。
- API 配置文件统一放入 `API配置文件/`，方便换电脑、发给同事、做本地迁移。
- 本地私密配置使用 `API配置文件/local-config.js`，并通过 `.gitignore` 避免误提交。
- 提供 `local-config.example.js` 模板，方便别人照着配置。
- 翻译侧支持百度翻译 API 配置，并保留本地词库兜底翻译。

这一步把“我电脑上能用”推进到了“换设备、换同事、换模型也能维护”的阶段。

### 5. UI 切图检测升级：从命名工具扩展为资产规范检查工具

V1.43 已经有检测模块雏形。V2.2 进一步把它变成独立能力：

- 主界面提供 UI 切图检测入口。
- 支持检测项目组切换。
- 支持检测模式切换。
- 支持查看检测规范说明。
- 支持只看问题图片、只看警告图片。
- 点击筛选后按警告或问题类型排序，便于集中处理同类问题。
- 检测规则支持 `.png` 格式规范提示。
- 支持分辨率双数检查。
- 支持单边 512px 以上 4 倍数规则。
- 支持 512px 以下图片非单数规则。
- 支持单边 2048px 黄色警告：允许上传但不推荐，建议切成两张 1024 拼接。
- 支持图标尺寸规范：正方形，且符合 32、64、128、256、512、1024 等规格。
- 支持策划配置切图规范：不能有 4 倍图片，都要 2 的幂次。
- 重复资源检测增加高中低灵敏度，并默认关闭，减少误报。

检测模块的定位已经从“辅助提醒”升级为“项目组切图提交前的第一道质量门”。

### 6. 下载导出升级：尊重原始图片，不擅自重编码

曾经尝试过标准 PNG 重编码来兼容 Windows 预览，但用户明确要求不要改动图片内容。

V2.2 已恢复为“原文件内容直接改名写出”：

- 下载命名完成图片时不重新编码。
- 不改变图片像素。
- 不改变图片压缩方式。
- 不做额外图像处理。
- 只做文件命名层面的输出。

这保证了导出的资源不会因为工具流程而引入不可控的图片差异。

### 7. 分发体验升级：让别人拿到项目也知道怎么打开

V2.2 将主入口改为中文文件：

- `点击启动服务.html`

同时保留：

- `index.html`

`index.html` 会自动跳转到中文启动文件，兼容本地打开、服务启动、GitHub 默认入口等不同使用方式。

## V1.43 与 V2.2 差异总览

| 能力项 | V1.43 | V2.2 |
| --- | --- | --- |
| 工程架构 | 单体 `app.js` | 模块化 `js/` 体系 |
| 大批量上传 | 容易卡死 | 分批上传、并发控制、懒加载预览 |
| 列表渲染 | 全量渲染压力大 | 分页式渲染，支持继续显示 |
| AI 命名 | 基础 AI 推荐 | AI + 本地知识库双模式 |
| 命名字段 | 工程名为主 | 前缀、工程名、界面名、序号拆分 |
| 项目配置 | 基础方案 | 项目与方案分离，多方案管理 |
| 词库 | 基础知识库 | 分类词库、标签页、可点选/取消 |
| 翻译 | 基础翻译 | 百度翻译配置 + 本地词库兜底 |
| AI 配置 | 本地填写 | 保存、测试、导入、导出、跨设备迁移 |
| 检测模块 | 初步检测 | 项目组、模式、规范说明、问题/警告筛选 |
| 重复检测 | 容易误报 | 灵敏度可调，默认关闭 |
| 下载导出 | 命名下载 | 原文件内容直接改名输出 |
| 启动入口 | `index.html` | `点击启动服务.html` + 兼容跳转 |

## 代码规模变化

从 V1.43 到 V2.2，工程发生了结构性变化：

- 变更文件：18 个
- 新增代码：约 4671 行
- 删除或迁移代码：约 4218 行
- 原 `app.js` 大量逻辑被拆分到独立模块

这不是单纯堆功能，而是一次把项目从“能用”往“能长期维护”推进的重构。

## 对使用者的实际收益

### 对普通使用者

- 打开更直观。
- 配置更容易迁移。
- 上传大量图片不容易卡死。
- 命名时可看 AI、可用词库、也可只用本地规则。
- 下载图片不会被重新编码。

### 对项目负责人

- 可以按项目组沉淀命名规范。
- 可以把检测规则显性化，减少口头沟通成本。
- 可以通过方案模板和配置文件统一团队标准。
- 可以提前发现分辨率、格式、重复资源等问题。

### 对后续开发维护

- 改 AI 不影响检测。
- 改检测不影响导出。
- 改词库不需要动上传流程。
- 改 UI 渲染不需要翻完整业务逻辑。
- 后续继续加项目组、模型、规范会更稳。

## 版本定位

V1.43 是一个功能逐渐丰满的工具版本。  
V2.2 是一个开始具备产品工程骨架的版本。

它已经不只是“帮我把图片改个名字”，而是开始承担这三个目标：

1. 帮 UI 资源建立可复用的命名秩序。
2. 帮项目组在提交前发现资产规范问题。
3. 帮不同电脑、不同用户、不同项目方案之间保持配置一致。

## 后续建议

- 版本号

这样项目会越来越像一个真正的内部工具产品，而不是散落在聊天记录里的功能堆叠。
